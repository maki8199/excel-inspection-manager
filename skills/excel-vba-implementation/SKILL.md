# Excel/VBA業務ツールの実装手順

要件書（と、あれば操作モック）から、Windows版デスクトップExcelで動く業務ツールを実装するための手順。特定の業務・案件には依存しない。HTMLの自動変換やWebアプリ開発は行わない。設計・ソース編集を含め、作業はすべてWindowsで行う。Excel/VBA・UserForm・外部連携・共有保存の合否判定は対象のWindows環境で行う。

このファイルは「作業の手順」を扱う。ソース・フォーム・ひな形の管理方法、スクリプトの入出力、AIエージェントが守る規則は `docs/code-and-workbook-management.md` に従う。

## When to Use

- 案件の要件書をもとにExcel/VBAを実装するとき。
- 業務操作を一つずつ追加し、実機で受入検証するとき。
- 対象外：HTMLだけの画面修正、汎用の表計算ファイル作成、Web版への置き換え。

## Prerequisites

- 案件の要件書（例：`docs/requirements.md`）を業務要件の正本として読む。このリポジトリには個別案件の要件書を含めない。
- 操作モックがある場合は、通常のブラウザーで開いて画面と操作を確認する。
- `docs/code-and-workbook-management.md` を読み、正本の置き場所とビルド・検証の流れを確認する。
- 本番検証には、Windows版Excel、マクロ実行が許可された検証環境、要件にある外部機器・導入済みソフトを用意する。
- 本番端末へ追加できるソフト・ライブラリの制約を確認する。開発側だけの補助ツールと本番依存物を区別する。
- 保存先・同時更新人数・権限・バックアップ先を確認する。未回答の事項を、単独利用などの推測で確定しない。
- 本番データ・外部機器・共有フォルダーに接続する前に、検証用データと実行範囲を合意する。

## How to Use

このファイルはリポジトリ同梱の手順書であり、自動インストール済みスキルとは扱わない。別のAIには、要件書・このファイル・管理ガイドを読ませてから着手させる。他の個人用スキルへのアクセスは不要。

依頼例：

    docs/requirements.md、skills/excel-vba-implementation/SKILL.md、
    docs/code-and-workbook-management.md を読み、Excel/VBA実装を進めてください。
    未確定事項は仮定で本番仕様にせず、最初に一つの業務の流れを入力から保存・再起動まで検証してください。

Hermesではファイル確認に `read_file` / `search_files`、新規作成に `write_file`、変更に `patch`、実行に `terminal` を使う。他の環境では対応する機能を使う。

## Procedure

### 1. 要件と受入条件を抽出する

- 要件書の未確定事項を確認する。計算式・単位・丸め、採番、保存構成、権限、外部連携など、実装を妨げるものを優先する。
- 要件書の受入条件をチェックリストとして使い、各要件に実装箇所と検証結果を対応させる。未実行は未検証のまま残す。
- モックの仮計算、仮の入力範囲、模擬時計、サンプル値を本番仕様として採用しない。
- モックと文書が食い違う場合は要件書を優先する。業務ルールが曖昧なら必要な点だけ確認する。
- 完了条件：着手範囲、確定事項、実装を妨げる未確定事項が分かれている。

### 2. 保存と外部連携の小さな実機検証を先に通す

- 全画面を作る前に、Windows版Excelでテスト記録の保存・終了・再起動・再読込を試す。
- 想定保存先で読み取り専用、更新競合、保存失敗を試し、成功していないのに完了と出さないことを確認する。
- 印刷など外部機器・外部ソフトとの連携がある場合は、保存済みの値を実際に渡して結果と照合する。連携方法は導入済みソフトの対応版と公式資料から確認し、未確認のAPIやコマンドを作らない。
- 要求、送信結果、実際の出力を区別する。検知できない結果は結果不明として扱う。
- 利用者が確認済みとした前提を聞き直さない。再検証の論点を絞る。
- 完了条件：保存と外部連携の成立条件が実機で分かる。環境がなければ設計・ソース作成までに限定し、実機確認を済ませたと報告しない。

### 3. 保存構成とデータを設計する

- 単独更新で要件を満たす場合は1ブック構成を最小候補とする。同時更新が必要なら先に排他・再読込・競合拒否を設計する。
- 台帳（現在の状態）と履歴を分ける。現在値、適用中の記録、採番を明示する。
- IDは対象の識別子として扱い、別の対象に再利用しない。修正で変更しない。
- 入力値、確定した計算結果、単位、計算ルール版、丸め条件を固定値として保持する。過去値を現在の式で再計算しない。
- 参照切れ・記録欠落・同時刻の競合は推測で補わない。
- 複数の台帳・履歴にまたがる更新は一つの業務操作として確定する。Excel保存だけで原子的になると仮定せず、途中失敗時の取消・再読込・復旧方法を設計して試す。
- 完了条件：保存項目と状態遷移が決まり、1操作の失敗で片側だけ残さない方針が検証可能になっている。

### 4. ブックとVBAの最小構成を作る

- 保存用シートと操作画面を分離する。台帳セルを通常操作で直接編集させない。非表示やシート保護をアクセス権・データ整合性の保証と扱わない。
- VBAは画面、業務操作、計算、保存、履歴、外部連携の責務を分ける。フォームのボタンに全処理を詰め込まず、不要な抽象化も増やさない。
- 最終成果物はマクロ有効ブックと再構築に必要なVBAソースとする。コード・フォーム・ひな形の正本と組み立て方は管理ガイドに従う。
- 対象Excelでコンパイルを確認する。拡張子を変更しただけのファイルや空のVBAプロジェクトを完成品にしない。
- 完了条件：対象Excelでブックが開き、実際のボタンからフォームを操作できる。

### 5. 一つの業務の流れを最初から最後まで動かす

- 最も基本的な流れを一つ選び、入力→計算→保存→（必要なら出力）→履歴の記録、を通す。
- 出力や後続処理は、保存済みのIDで対象を特定する。表示文字、未保存入力、別の対象の値を元にしない。
- 要件にない画面・確認ダイアログ・ボタンを追加しない。
- キャンセル・×・Escapeは下書きだけを捨て、台帳・採番を変更しない。
- 完了条件：実Excel、実際の出力、履歴の値が一致し、終了・再起動後も同じ記録と状態が残る。

### 6. 残りの業務操作を小さく追加する

- 修正・削除・取消など、残りの操作を要件書の優先順に一つずつ追加する。
- 修正は旧記録を保持して新記録を追加する。削除は論理的な終了として履歴を残す。
- 複数の対象を同時に変える操作は一緒に確定する。実行直前に対象が変わっていたら拒否し、別の操作へ勝手に読み替えない。
- 各機能を追加するたびに、全履歴・取消・失敗時の不変性を確認する。
- 完了条件：各操作の正常系と重要な異常系が対象Excelで再現・検証されている。

### 7. 実機受入と配布を行う

- 要件書の受入条件を漏れなく照合する。計算の既知の確認例、丸め境界、時刻境界、競合、参照切れを確認する。
- 保存失敗・共有先切断・更新競合・外部連携の失敗・結果不明・途中終了を検証し、誤った完了表示や二重操作を防ぐ。
- 対象端末の表示倍率、画面サイズ、入力方法でフォームとボタンを確認する。想定件数のデータで性能を測る。
- 既存データは合意した範囲だけ取り込み、件数・ID・数値・参照関係を確認する。記録されていない過去は捏造しない。
- バックアップから実際に復旧して確認する。マクロ設定は組織の方針に従い、全面的な保護無効化を要求しない。
- 配布物は動作するブック、VBAソース、実際に必要なテンプレート、短い操作・復旧手順、実測の検証結果に絞る。
- 完了条件：受入項目ごとに合格・未確認・制限が分かり、利用者が同じ環境で開始・復旧できる。

## Pitfalls

- HTMLモックの成功はVBA・外部連携・永続保存の成功ではない。
- 存在しないファイルやコマンドを前提にしない。管理ガイドのスクリプトは、導入先で実装するまで存在しない。
- モック上の確認用機能（コメント機能など）は本番Excelの必須機能ではない。
- ボタン操作の完了と、現物・外部機器での結果は別の出来事。操作だけで現物が一致したと保証しない。
- 保存・外部連携の都合で、利用者が削った中間確認や入力欄を無断で復活させない。
- 認証情報、実業務台帳、共有先の秘密情報、実データ入りブックをリポジトリへ含めない。

## Verification / 報告

報告は「実装したもの」「自動テストで確認したもの」「Windows実機で確認したもの」「未検証・阻害要因」を分ける。モックだけ、ソースだけ、コンパイルだけで完成としない。

完了時には成果物の場所、実行した検証と結果、残る条件だけを簡潔に示す。実行できなかった結果を模擬出力で埋めない。
