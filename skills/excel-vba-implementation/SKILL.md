# 点検基準管理ツールのExcel実装手順

仕様書とHTMLモックから、Windows版デスクトップExcelで動くツールを実装するための手順。HTMLの自動変換やWebアプリ開発は行わない。設計・ソース編集は各OSで可能だが、本番のExcel/VBA・UserForm・印刷・共有保存の合否判定は対象Windows環境で行う。

## When to Use

- このプロジェクトの仕様書とモックをもとにExcel/VBAを実装するとき。
- 登録・修正・移動・履歴・印刷の機能を追加し、実機で受入検証するとき。
- 対象外：HTMLだけの画面修正、汎用の表計算ファイル作成、Web版への置き換え。

## Prerequisites

- プロジェクトルートの `docs/requiements.md` を業務要件の正本として読む。ファイル名はこの綴りのまま扱う。
- `mock/index.html` を通常のブラウザーで開き、画面と操作を確認する。
- 本番検証には、Windows版Excel、マクロ実行が許可された検証環境、SR5900P、導入済み純正ソフト・ドライバー、テスト用テープを用意する。
- 外部ライブラリを本番端末へ追加しない条件を守る。開発側だけの補助ツールと本番依存物を区別する。
- 保存先・同時更新人数・権限・バックアップ先を確認する。未回答の事項を、単独利用などの推測で確定しない。
- 本番台帳・プリンター・共有フォルダーに接続する前に、検証用データと実行範囲を合意する。

## How to Use

このファイルはリポジトリ同梱の手順書であり、自動インストール済みスキルとは扱わない。別のAIには、仕様書・このファイルを読ませてからモックを確認させる。他の個人用スキルや元のWeb試作へのアクセスは不要。

依頼例：

    docs/requiements.md と skills/excel-vba-implementation/SKILL.md を読み、
    mock/index.html を操作見本としてExcel/VBA実装を進めてください。
    未確定事項は仮定で本番仕様にせず、最初に1個体の登録から実印刷・履歴・再起動まで検証してください。

Hermesではファイル確認に `read_file` / `search_files`、新規作成に `write_file`、変更に `patch`、実行に `terminal` を使う。他の環境では対応する機能を使う。

## Procedure

### 1. 要件と受入条件を抽出する

- 仕様書第16節の未確定事項を確認する。正式な測定項目・計算式・単位・丸め、採番、保存構成、作業者、現物切替時刻、印刷連携を優先する。
- 第17節を受入チェックリストとして使い、各要件に実装箇所と検証結果を対応させる。未実行は未検証のまま残す。
- モックの仮計算、仮の入力範囲、模擬時計、サンプル値を本番仕様として採用しない。
- モックと文書が食い違う場合は仕様書を優先する。業務ルールが曖昧なら必要な点だけ確認する。
- 完了条件：着手範囲、確定事項、実装を妨げる未確定事項が分かれている。

### 2. 保存と印刷の小さな実機検証を先に通す

- 全画面を作る前に、Windows版Excelでテスト記録の保存・終了・再起動・再読込を試す。
- 想定保存先で読み取り専用、更新競合、保存失敗を試し、成功していないのに完了と出さないことを確認する。
- Excelの保存済み上下限・単位からSR5900Pへ値を渡し、実際の印字と照合する。印刷連携は導入済みソフトの対応版とメーカー公式資料から確認し、未確認のAPIやコマンドを作らない。
- 15mm角へ必要な値を印刷できることは確認済み。再検証の論点は自動連携・正しい対象・設定であり、印刷可否の前提を聞き直さない。
- 印刷要求、送信結果、実出力、貼付照合を区別する。検知できない出力は結果不明として扱う。
- 完了条件：保存と自動印刷の成立条件が実機で分かる。環境がなければ設計・ソース作成までに限定し、実機確認を済ませたと報告しない。

### 3. 保存構成とデータを設計する

- 単独更新で要件を満たす場合は1ブック構成を最小候補とする。同時更新が必要なら先に排他・再読込・競合拒否を設計する。
- セット台帳、個体台帳、確定値履歴、使用履歴、補助のラベル発行履歴を分ける。現在配置、適用中記録、貼付待ち記録、採番を明示する。
- 個体IDは実物の識別子。別実物に再利用しない。修正と移動で変更しない。
- 入力値、確定上下限、単位、計算ルール版、丸め条件を固定値として保持する。過去値を現在の式で再計算しない。
- 使用履歴は管理No.＋位置＋切替日時を基本にする。終了日時は次の切替から導出し、開始を含み終了を含まない。
- 停止・空き・廃止も記録し、有効な上下限を表示しない。同時刻競合・参照切れ・記録欠落は推測で補わない。
- 採番、配置、測定記録、関連履歴を一つの業務操作として確定する。Excel保存だけで原子的になると仮定せず、途中失敗時の取消・再読込・復旧方法を設計して試す。
- 完了条件：保存項目と状態遷移が決まり、1操作の失敗で片側だけ残さない方針が検証可能になっている。

### 4. ブックとVBAの最小構成を作る

- 操作シートは「セット管理」「使用履歴」。8枠は図形ボタン、登録・修正・詳細・移動はUserFormを基本とする。
- 保存用シートと操作画面を分離する。台帳セルを通常操作で直接編集させない。非表示やシート保護をアクセス権・データ整合性の保証と扱わない。
- VBAは画面、業務操作、計算、保存、履歴、印刷の責務を分ける。フォームのボタンに全処理を詰め込まず、不要な抽象化も増やさない。
- 最終成果物はマクロ有効ブックと再構築に必要なVBAソースとする。標準モジュール・クラス・フォームをエクスポートし、フォームに付随するバイナリがある場合は一緒に保管する。
- 初期構築・インポート方法と文字コードを記録し、対象Excelでコンパイルを確認する。拡張子を変更しただけのファイルや空のVBAプロジェクトを完成品にしない。
- 完了条件：対象Excelでブックが開き、実際のボタンからフォームを操作できる。

### 5. 1個体を最初から最後まで動かす

- セット作成→空き枠→入力→計算→保存→貼付待ち→個体詳細から即発行→現物貼付照合→同じ詳細内で完了→使用履歴、を通す。
- ラベルは保存済みの個体ID・記録IDで特定する。表示文字、未保存入力、別個体の値を印刷元にしない。
- 保存だけ・発行だけで使用中にしない。貼付照合完了で使用開始を記録する。
- 専用ラベル画面、二度目の発行ボタン、QR読み直し、不要な確認画面を追加しない。
- キャンセル・×・Escapeは下書きだけを捨て、台帳・採番を変更しない。
- 完了条件：実Excel、実ラベル、履歴の値が一致し、終了・再起動後も同じ記録と状態が残る。

### 6. 残りの業務操作を小さく追加する

1. 修正：同じ個体に新記録を追加。旧記録を保持し、貼り替え・照合まで使用停止。
2. 削除・置き換え：論理的な使用終了と空き履歴を残し、次の実物は新ID。
3. 移動・交換：双方の配置・切替履歴を一緒に確定。過去履歴は元の位置へ残す。実行直前に対象が変わっていたら拒否し、移動を勝手に交換へ変えない。
4. 廃止：セットと各位置の使用を停止し、履歴閲覧だけを残す。
5. 再発行：発行履歴を追加し、同じ適用記録の再印刷で測定版・使用期間を増やさない。

各機能を追加するたびに、位置別の全履歴・取消・失敗時の不変性を確認する。現物移動と時計・後追い記録の運用は合意した手順に従う。

完了条件：各操作の正常系と重要な異常系が対象Excelで再現・検証されている。

### 7. 実機受入と配布を行う

- 仕様書第17節を漏れなく照合する。正式式の既知の確認例、丸め境界、停止期間、時刻境界、同時刻競合、参照切れ、再印刷を確認する。
- 保存失敗・共有先切断・更新競合・印刷失敗・結果不明・途中終了を検証し、誤った完了表示や二重操作を防ぐ。
- 対象タブレットの表示倍率、画面サイズ、タッチ操作でフォームとボタンを確認する。想定件数の全履歴を表示して性能を測る。
- 既存データは合意した範囲だけ取り込み、件数・ID・数値・参照関係を確認する。記録されていない過去は捏造しない。
- バックアップから実際に復旧して確認する。マクロ設定は組織の方針に従い、全面的な保護無効化を要求しない。
- 配布物は動作するブック、VBAソース、実際に必要な印刷テンプレート、短い操作・復旧手順、実測の検証結果に絞る。
- 完了条件：受入項目ごとに合格・未確認・制限が分かり、利用者が同じ環境で開始・復旧できる。

## Pitfalls

- HTMLモックの成功はVBA・実印刷・永続保存の成功ではない。
- このリポジトリには現在、Excel実装・旧Webサーバー・業務DB・ビルド環境はない。存在しないファイルやコマンドを前提にしない。
- UI確認のための囲みコメントは本番Excelの必須機能ではない。モックの既存コメントは移動後のファイルから自動復元できると約束しない。
- 普段の点検は数値ラベルで行う。QR点検シートや点検結果の二重入力を復活させない。
- 印刷・貼付照合・現物配置は別の出来事。ボタン操作だけで現物が一致したと保証しない。
- 保存・印刷の都合で利用者が削った中間確認や入力欄を無断で復活させない。
- 認証情報、実業務台帳、共有先の秘密情報、実データ入りブックを公開リポジトリへ含めない。

## Verification / 報告

報告は「実装したもの」「自動テストで確認したもの」「Windows実機で確認したもの」「未検証・阻害要因」を分ける。モックだけ、ソースだけ、コンパイルだけで完成としない。

完了時には成果物の場所、実行した検証と結果、残る条件だけを簡潔に示す。実行できなかった結果を模擬出力で埋めない。
