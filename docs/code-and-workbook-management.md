# Excel/VBA開発のコード・フォーム・シート管理ガイド（汎用）

## この文書の位置付け

Windows版ExcelとVBAで開発する業務ツールに適用できる、汎用的なソース・画面・版管理のガイドです。特定の業務、既存リポジトリ、個人環境への依存はありません。

本ガイドでは、シートはExcelひな形を正本とし、発行済みブックのシート編集は取り込まず、ひな形側で変更して確認後に新版を発行する運用を採用します。変更前の一式を保持し、ひな形・コード・フォームを同じ版として管理します。

本書は運用方針と構成例を示すもので、完成したビルドツールの配布物ではありません。記載したスクリプトやブックは作成済みではなく、ビルド・変更取り込み・対象Windows環境での動作は、導入先で実装・検証する必要があります。

業務要件・入力権限・保存期間などは、導入先の要件書で別途定めます。本書を他のプロジェクトへ持ち出す際に、元プロジェクトの要件書を同封する必要はありません。開発上の編集手順は、本番データの直接編集を許可するものではありません。

## 1. 管理の基本方針

対象ごとに、編集・復元の基準となる正本を一つに決めます。

| 管理対象 | 正本 |
|---|---|
| 標準・クラスモジュールのコード | 外部のテキストファイル |
| シート・ThisWorkbookのコード | 外部のテキストファイル |
| UserFormの画面とコード | 初回生成後は `.frm`＋`.frx` |
| シートの見た目・構造 | Excelひな形。発行済みブックの編集は取り込まない |
| 本番データ | アプリの更新とは分離して保持 |

同じ内容をJSONとExcelの両方で正本として管理するなどの二重管理は避けます。

### 推奨フォルダ構成

以下は別のExcel/VBA案件にも使える構成例です。ファイル名は例示であり、本書の保存先にこれらが実在するという意味ではありません。必要なものだけ作成し、UserFormや独自クラスを使わない案件では該当フォルダを省略できます。

```text
excel-vba-project/
├── README.md                         # 開発環境・ビルド・編集・復元の入口
├── .gitignore                        # 作業用コピー・生成物・端末固有設定を除外
├── docs/
│   ├── requirements.md               # 導入先の業務要件
│   ├── code-and-workbook-management.md # 本ガイドまたは案件への適用方針
│   └── release-notes.md              # 版ごとの変更内容・確認結果
├── templates/
│   └── application.xlsm              # シートの見た目・構造の正本
├── src/
│   ├── modules/
│   │   ├── AppMain.vba               # 標準モジュール
│   │   └── Validation.vba
│   ├── classes/
│   │   └── Record.vba                # 必要な場合だけ独自クラス
│   ├── workbook/
│   │   └── ThisWorkbook.vba          # ブックオブジェクトのコード
│   ├── worksheets/
│   │   ├── SheetMain.vba             # シートオブジェクトのコード
│   │   └── SheetHistory.vba
│   └── forms/
│       ├── EntryForm.frm             # フォームの正本（コードを含む）
│       ├── EntryForm.frx             # 同じフォームの付随ファイル
│       ├── SearchForm.frm
│       └── SearchForm.frx
├── scripts/
│   ├── build.ps1                     # 正本から候補ブックを組み立てる
│   ├── export-edits.ps1              # 編集済みExcelからコード・フォームを書き出す
│   └── verify.ps1                    # ファイル構成のチェックと実装済み自動テストの実行
├── tests/
│   ├── acceptance.md                 # 動作・見た目の確認チェックリスト
│   └── fixtures/                     # 自動テスト用の架空データ（必要な場合だけ）
├── work/                             # ひな形の編集コピー・変更取り込み候補
└── dist/
    └── application.xlsm              # 生成物。検証合格前は配布しない
```

`templates/application.xlsm` と `dist/application.xlsm` は別の役割です。前者がシートの正本、後者はコード・フォームを組み込んだ生成物です。`dist/` のブックを新たなひな形として逆取り込みしません。

### 各フォルダの管理方法

| 場所 | 内容・編集方法 | 通常のGit管理 |
|---|---|---|
| `README.md`、`docs/` | 開発手順、要件、版の記録。人間またはAIが編集 | 対象 |
| `templates/` | シートの正本。`work/` にコピーして変更・確認後に採用 | 対象 |
| `src/modules/`、`src/classes/` | 標準・クラスモジュールのコード。テキストを編集 | 対象 |
| `src/workbook/` | ThisWorkbookのコード。テキストを編集 | 対象 |
| `src/worksheets/` | 各シートオブジェクトのコード。テキストを編集 | 対象 |
| `src/forms/` | 正本のフォーム一式。作業用Excelで編集し、再エクスポートして更新 | 対象 |
| `scripts/` | ビルド・コードとフォームの書き出し・検証の処理。ひな形や本番データの無断上書きを避ける | 対象 |
| `tests/` | 検証手順と架空データ。本番ファイルのコピーを置かない | 対象 |
| `work/` | 候補版、一時エクスポート、検証結果。正本ではない | 対象外 |
| `dist/` | 生成したブック。正式配布物の保管先とは区別 | 通常は対象外 |

スクリプト名と役割は設計例です。コマンドとしてすでに実行できるとは扱いません。小さな案件では処理を一つのスクリプトへまとめてもかまいません。

### 編集済みExcelからの書き出し：export-edits.ps1

`export-edits.ps1` は、編集済みExcelから対象のコード・UserFormを書き出し、`work/` に保存する処理を想定します。この段階では `src/` の正本を上書きしません。

「変更箇所だけを自動判定して抜き出す」という意味ではありません。まず対象のモジュールやフォームを書き出し、その後に現在の正本と比較します。

```text
編集済みExcel
  → 対象のコード・フォームを書き出す
  → work/extracted/へ保存する
  → 現在のsrc/と比較する
  → 採用する変更だけsrc/へ反映する
```

書き出し先の例：

```text
work/
└── extracted/
    ├── modules/
    │   └── AppMain.vba
    └── forms/
        ├── EntryForm.frm
        └── EntryForm.frx
```

クラス・ブック・シートのコードを書き出す場合も、`src/` と対応するフォルダへ保存する設計にします。フォーム以外のコードは、本ガイドの `.vba` 形式に合わせたコード本文として出力する処理が必要です。エクスポート済みファイルの拡張子を変えるだけで済むとは扱いません。

書き出しと、変更を正本へ採用する判断は別の作業です。比較・採用は第5節に従います。発行済みシートのレイアウトや構造を取り込む処理は含めません。

### ファイル構成のチェックと自動テスト：verify.ps1

`verify.ps1` は、次の二つを実行するための処理を想定します。

**ファイル構成・組み込み結果のチェック**

- ひな形が存在するか。
- フォームが参照する `.frx` がそろっているか。
- 組み込むモジュール名が重複していないか。
- シートコードの書き込み先が存在するか。
- ビルド後のブックに必要なモジュールやフォームがあるか。
- 削除したはずの古い管理対象部品が残っていないか。

**あらかじめ実装した自動テストの実行**

- 計算処理：決めた入力を渡して実行し、期待結果と一致するか比較する。
- 保存処理：検証用ブックへ保存し、開き直して値が残っているか確認する。

これらは実装する検査の例であり、現時点で実行済みの検査ではありません。`verify.ps1` を置くだけで全機能を自動検証できるわけではなく、テストを実装していない機能は未検証のままです。テストは検証用ブック・データで行い、本番データを変更しません。対象Windows版Excelでの表示・操作確認は、第7節の検証手順と併せて行います。

### チェックリストとテストデータ

- `tests/acceptance.md`：動作・見た目の確認チェックリストです。例えば「フォームが画面からはみ出さない」「キャンセルで保存されない」「保存後に開き直しても値が残る」などを記載します。チェックリストを置くだけではテストは実行されません。確認結果と未確認項目を区別して記録します。
- `tests/fixtures/`：自動テストで使う架空の入力データや期待結果を置きます。必要になった場合だけ用意し、本番データは使用しません。

### 初回フォーム生成時だけ使うファイル

初回に定義とコードからフォームを生成する場合だけ、次の入力を追加します。

```text
bootstrap/
└── forms/
    └── EntryForm/
        ├── layout.json              # 部品・位置・サイズなど
        └── code.vba                 # 初回生成用のフォームコード
```

生成後にエクスポート・再取り込み・動作確認が完了したら、`src/forms/EntryForm.frm` と対応する `.frx` を正本に切り替えます。`bootstrap/forms/EntryForm/` は現行ファイルから削除し、履歴だけ残します。

後から新しいフォームを追加する場合も、そのフォームだけ初回生成用フォルダを作り、同じ手順で切り替えます。既存フォームを古い生成定義から作り直しません。通常のビルドはフォームの組み込み元として `src/forms/` を読み、初回生成処理とは分けます。

### 開発フォルダの外へ置くもの

本番データとバックアップは、社内で承認された別の保管先へ置きます。以下は役割を示す例であり、具体的なパスやデータ保存方式は導入先で決めます。

```text
社内の承認済み保管先/
├── releases/                        # 検証済み配布物。版・元コミットと対応付ける
├── production-data/                 # 運用中のデータ。ソース管理へ入れない
└── backups/                         # 本番データの復旧用。ソースの履歴とは別管理
```

`releases/` と `production-data/`、`backups/` を同じ物理的な場所へ置くことを要求する図ではありません。アクセス権やバックアップ先は社内ルールに従います。個人情報・認証情報・実業務データ・端末固有の接続設定を、開発用ひな形や共有するソースへ混在させません。

### Git除外設定の例

```gitignore
# 作業用コピー・生成物
/work/
/dist/

# Excelの一時ファイル・OSの管理ファイル
~$*
*.tmp
.DS_Store
Thumbs.db

# 個別環境の設定・認証情報
.env
.env.*
!.env.example
*.local.*

# 本番データ等を誤って開発フォルダへ置いた場合の補助的な除外
/production-data/
/backups/
```

`*.xlsm` や `*.frx` を一律除外すると、正本のひな形やフォームまで管理できなくなるため、この例では除外しません。`work/` や `dist/` がGit管理外でも、内容が不要になったとは限りません。正本への採用・正式保管が済む前に削除しないでください。

除外設定は、すでに追跡されたファイルの機密情報除去やバックアップを代替しません。コミット前の対象確認と、正式配布物・本番データの別途保管を行います。

## 2. VBAコードの管理

フォーム以外のコードは、例えば次の構成で保存します。このディレクトリ構成は提案であり、作成済みではありません。

```text
src/
  modules/
    Validation.vba
    AppMain.vba
  classes/
    Record.vba
  workbook/
    ThisWorkbook.vba
  worksheets/
    SheetMain.vba
    SheetHistory.vba
```

`.vba` は、コード本文を保存するために採用する拡張子です。拡張子自体に特別な機能はありません。

PowerShellがファイルの中身をテキストとして読み、COM経由で対象モジュールへ書き込みます。

| 情報 | 決め方 |
|---|---|
| モジュールの種類 | フォルダ名 |
| モジュール名 | ファイル名 |
| VBAコード | ファイル本文 |

全ファイルの名前を別の管理用JSONへ重複登録することは、最小構成では行いません。

### シート・ブックモジュール

`src/workbook/` はThisWorkbook、`src/worksheets/` は各シートオブジェクトのVBAコードだけを管理します。シートの見た目、テーブル構造、名前定義などはここへ保存せず、`templates/` のExcelひな形で管理します。

シート・ThisWorkbookのコードは、対象に付属するモジュールを特定して書き込みます。通常のクラスとして新規追加する方式とは区別します。

シートの表示名とコードの組み込み先との対応は明確に決め、タブ名とCodeNameを混同しません。

Excelひな形の中にコードが残っていても、それをコードの正本にはしません。ビルド時に管理された外部ソースで置き換える方針です。

### コード本文とエクスポート形式の区別

この方式は、Excelからエクスポートした `.bas` や `.cls` をそのままImportする方式とは異なります。

コード本文だけでは再現できない属性が必要になった場合は、その扱いも設計します。エクスポート情報を一律に不要として削除する方針ではありません。

## 3. UserFormの管理

初回は定義とコードから自動生成し、その後はエクスポートしたフォームを正本にする方向です。

### 初回生成：方式A

```text
JSONで部品・配置を定義
  ＋ .vbaでフォームの処理を記述
  → COM経由でフォームを生成
  → .frm＋.frxへエクスポート
  → 別ブックへの取り込み・表示・動作を確認
  → 正本を.frm＋.frxへ切り替える
```

JSONには、フォームの大きさ、部品の種類・名前・位置・サイズ・表示文字などを記述します。VBAコードは別のテキストに記述します。

初回ビルド前に `.frm`＋`.frx` を直接作成する方式ではありません。Excel内でフォームを生成した後に書き出します。

### 正本切り替え後：方式B

```text
src/forms/
  EntryForm.frm
  EntryForm.frx
  SearchForm.frm
  SearchForm.frx
```

フォームのコードも、この組に含めて管理します。同じフォームのコードを別の `.vba` でも重複管理しません。

切り替えの検証が完了したら、不要になった初回生成用JSONとフォーム用 `.vba` は現行ファイルから削除します。必要な場合はGitの過去履歴を参照します。

この削除対象は、そのフォームの生成定義と重複コードです。標準モジュールのソースや、別用途の設定ファイルまで削除する意味ではありません。

### 2回目以降の修正

```text
正本の.frm＋.frxを作業用Excelへ取り込む
  → 人間またはAIが編集する
  → 表示・操作を確認する
  → 再エクスポートする
  → 正本を更新する
```

AIが修正する場合も、`.frx` のバイナリを直接書き換えるのではなく、Excel内のフォームをCOM経由で操作する方針です。

全フォームのフォント変更、部品追加、配置変更なども、この編集処理として扱います。文字サイズを変えた場合は、文字切れや部品の重なりなども確認します。

大幅な変更でフォームを作り直す場合は、既存イベント処理、部品名、外部コードからの参照を引き継ぐか明示的に変更します。古いJSONを無条件に再利用して、途中の編集を失わないようにします。

## 4. シートの管理

シートの見た目や構造は、Excelひな形を正本にします。変更はひな形側で行い、発行済みブックで行われたシート編集を正本へ取り込む運用は行いません。

### ひな形で管理するもの

- セルの固定文言、書式、色、罫線。
- 列幅、行高、レイアウト。
- 図形やボタンの配置。
- テーブルの構造。
- 名前定義。
- 印刷設定など。

ユーザーもAIも、正本のひな形から作った編集用コピーをExcel上で編集します。変更後はコード・フォームを組み込んだ候補版で確認し、問題なければ新しいひな形として採用して新版を発行します。

発行済みブックで行った色・配置・固定文言・テーブル構造・名前定義などの変更は、正本へ反映しません。必要な修正はひな形側で行います。発行済みシートとの差分抽出・逆取り込み・変更統合の仕組みは作りません。

この制限はシートの見た目・構造の編集に対するものです。業務仕様で認められたフォームや入力領域でのデータ登録・更新など、通常の業務操作を禁止するものではありません。また、シートモジュールのVBAコードは外部テキストを正本とする別の管理対象です。

この方式では、同じレイアウトをJSONにも記述する必要はありません。

処理が参照しているテーブル名、列名、名前定義、部品名などを変更した場合は、コード側への影響を確認します。

## 5. コード・UserFormをExcel内で直接変更した場合

この節はコードとUserFormの直接編集・取り込みを対象とします。本ガイドのシート管理方針により、この取り込み方針まで廃止するものではありません。ただし、取り込み処理は未実装です。

コード・UserFormをExcel内で試しに修正した場合、そのファイルだけで変更を終わらせず、対応する正本へ戻す想定です。発行済みブックのシートの見た目・構造の変更は対象外とし、第4節のとおりひな形側で変更します。

```text
ユーザーがExcel内のコード・UserFormを編集して保存
  → AIへ取り込みを依頼
  → AIが変更内容を確認
  → 対応する正本へ反映
  → 再ビルドして再現を確認
```

### 変更の反映先

| 変更した対象 | 正本への反映先 |
|---|---|
| 標準・クラス・シート・ブックのコード | 外部のコードファイル |
| UserForm | `.frm`＋`.frx` |

コード・UserFormの取り込みは自動同期ではありません。AIが取り込みを担当し、衝突や意図が曖昧な変更だけユーザーに確認する運用です。

生成ブックには元の版・コミットを記録する設計とし、古い版を編集したファイルで、最新の正本を無条件に上書きしないようにします。

必要な場合は、次の三つを比較して採用する変更を決めます。

1. 編集対象のブックを生成した時点の正本。
2. ユーザーが変更したブック。
3. 現在の正本。

コード・UserFormの抽出・比較・反映を行う取り込み処理は、ビルド処理と併せて実装する必要があります。コードやフォームの任意の変更を、常に自動で正確に統合できるとは扱いません。シートの見た目・構造は、この比較・取り込みの対象に含めません。

## 6. 正本の更新とバックアップ

変更前のひな形・コード・フォームを一組で保持し、正本へ直接上書きせずに次版候補を作ります。シート変更では、ひな形の編集用コピーを用意して次の手順を実施します。

```text
現在のひな形・コード・フォームの一式を保存
  → ひな形の編集用コピーを作る
  → ひな形側でシートを変更する
  → 対応するコード・フォームを組み込んで候補版を作る
  → 表示・動作を確認する
  → 問題なければ新しい正本として採用し、新版を発行する
```

例えば、現在の正本が `v003` なら、それは変更せずに残し、`v004候補` へ反映します。確認に失敗した場合は候補を破棄し、採用後に問題が見つかった場合は過去版へ戻せるようにします。

### 版ごとに一組で残すもの

- Excelひな形。
- VBAソース。
- `.frm`＋`.frx`。
- 変更メモと元の版。
- 必要に応じて、その版の配布用ブック。

Gitでは、ひな形・コード・フォームがそろった状態を同じ版として記録し、対応するコミットやタグから一式を取り出せるようにします。版ごとにフォルダを手作業で複製し続けることを必須にはしません。

ExcelファイルもGitで版管理できます。ただし、シートの見た目や `.frx` は、コードのような細かい差分確認・部分的な取り消しが難しいため、ブック全体の保存と表示確認を併用します。

「過去版へ丸ごと戻す」と「一部の変更だけ戻す」は区別し、後者は原則として新しい修正として扱います。

シートとコードに依存関係がある場合、片方だけ古い版に戻さないようにします。最初は複数人・AIによる同時編集を避け、一度に一つの変更を進める運用を基本候補とします。

## 7. ビルドの流れ

正本から配布用Excelを作る処理は、次の構成です。

```text
Excelひな形を作業用にコピー
  → 外部の標準・クラスモジュールを組み込む
  → シート・ThisWorkbookのコードを組み込む
  → .frm＋.frxを取り込む
  → バージョン情報を記録
  → .xlsmとして保存
  → 開き直して検証
  → 合格したものを配布する
```

ひな形に残る古いコードやフォームを重複して組み込まないよう、置き換え対象を明確にします。管理対象外の部品を無条件に削除する処理にはしません。

### 検証する内容

- 必要なシート、モジュール、フォームが存在する。
- コンパイルが通る。
- ボタンから目的の処理・フォームが開く。
- 変更した機能が動作する。
- 変更していない主要機能が壊れていない。
- 保存・再起動後も期待する状態を保持する。
- シートやフォームの文字切れ、重なり、操作しづらさがない。

ビルド処理が終了しただけで完成とはせず、対象Windows版Excelで確認します。

## 8. 本番データの扱い

画面やコードを戻しただけで、本番データまで過去に戻らないようにします。

現時点では、次の分離案を推奨しています。

```text
操作用.xlsm
  画面、フォーム、コード

データ用.xlsx
  マスタ、業務レコード、操作履歴など
```

ファイル分割、共有保存、排他制御は未確定です。この構成だけで同時更新や保存整合性が保証されるとは扱いません。

### 見た目だけの変更

ひな形側でレイアウトを変更して新版を発行し、同じデータを新しい操作ブックで読みます。発行済みブックのシート編集を取り込む処理は行いません。画面のセル位置ではなく、レコードIDや項目の意味に基づいてデータを扱う設計にします。

データ形式が同じ場合、操作ブックだけ旧版へ戻し、その間に登録した本番データは保持する運用を目指します。

### データ構造も変更する場合

保存項目やデータ構造が変わる場合は、別途データ移行を行います。

```text
データのコピーで移行を試す
  → 既存のID・値・履歴を照合
  → 本番更新を一時停止
  → 本番データをバックアップ
  → 合意した移行処理を実行
  → 新しい操作ブックで確認
  → 利用再開
```

過去に記録されていない値は推測で埋めません。データ構造変更後に旧アプリへ戻せるかは、互換性を別途確認します。

1ブック構成を選ぶ場合は、更新時のデータ引き継ぎ処理が必要です。

### 社内の管理環境と本番データの分離

会社内での開発・運用には、社内で承認された保存先・版管理環境を使用します。公開リポジトリは使用しません。本文のGitによる版管理は、公開GitHubへのアップロードを意味せず、社内で利用が認められた環境で行う想定です。具体的な製品・保存先は別途決めます。

実業務データは所定の社内保存先で管理し、開発用ひな形やソースへ混在させません。シート変更はひな形側で行い、本番ファイルやシートを丸ごと正本へ取り込む運用は行いません。コード・UserFormの取り込みやひな形の編集でも、実データや端末固有の秘密情報を一緒に反映しないように確認します。

- UserFormの生成・エクスポート・インポート・再編集の一連の実機検証。

## 10. 方針の要約

- コードは外部テキストで管理する。
- フォームは初回生成後、検証してから `.frm`＋`.frx` を正本にする。
- シートの見た目・構造はExcelひな形を正本とし、ユーザーもAIもひな形側で変更する。
- 発行済みブックのシート編集は取り込まない。通常の業務データ登録・更新とは区別する。
- コード・UserFormの直接編集は、シート管理とは分けて対応する正本へ戻す方針とする。
- 変更前のひな形・コード・フォームを保持し、次版候補で確認してから新版を発行する。その版の一式をまとめて管理する。
- アプリの版管理と本番データの保全を分ける。

ひな形をExcel上で直接調整する柔軟さを残しつつ、発行済みシートからの取り込みは行わず、コードの変更履歴と、画面を含む過去版への復元手段を持たせます。この運用を採用する場合も、導入先でビルド・取り込み・復元の一連の動作を実機検証してから運用を開始します。
